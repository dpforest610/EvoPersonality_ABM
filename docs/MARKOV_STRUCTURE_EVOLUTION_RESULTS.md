## p値の書き方について

不確かさはseed単位のブートストラップ(70 seedを復元抽出で2000回選び直す)によって評価しており、
片側p値は `p = (差が0以下になった回数 + 1) / (2001)` で計算される(事前登録5節の片側検定の定義に、
0除算を避けるための+1補正[Davison & Hinkley 1997の標準的な慣行]を加えたもの)。したがって
**2000回のブートストラップのうち1回も「差が0以下」にならなかった場合、p値はこれ以上小さくできる
保証がなく、観測可能な最小値 1/2001 ≈ .0005 の「上限」としてしか報告できない**。本報告では、
この最小値に一致する場合は `p < 1/2001` と表記し、実際にいくつかのブートストラップ差が0以下に
なった場合のみ `p = .xxxx` の形で具体的な値を示す(同様に、ほぼ全回が0以下だった場合は
`p > 2000/2001` と表記する)。

## 4. 探索的・事前登録外:GradualAppeasementの「なだめ」が実際に発動しているかの検証

(この節は事前登録にない追加調査であり、ユーザーからの個別の依頼に基づく。確証的結果にも
副次・記述的分析[6節]の各項目にも影響しない。)

### 調査方法

パイロットのプローブ記録(`scripts/output/markov_sweep_pilot_noise01/`・`noise00/`、
Gradual/GradualAppeasementとも同一個体群に対して実際に対戦させた生の`own_move`/`opp_move`系列
[クラウドにあるためMac不要])から、複数のseed・時点にまたがる**32ファイル・30,420対戦
(genotype×repeat)**を抽出し、2通りの検証を行った:

1. **実装の再現性チェック**: `evopersonality_abm/strategies.py`の`make_gradual_strategy`の
   状態機械を独立に再実装し、記録されている対戦相手の実際の手(genotypeの`own_move`系列)を入力して
   再生し、`appeasement=True`での出力が実際に記録されたGradualAppeasementの手と一致するかを確認。
2. **直接比較**: 同じ(genotype_id, repeat)の組について、実際に記録された`Gradual`
   (なだめなし)の対戦相手の手の系列と、`GradualAppeasement`の手の系列を、**コードを介さず
   生データ同士で**直接比較。

### 結果

| 指標 | 値 |
|---|---|
| 再生した対戦数 | 30,420 |
| 再生結果と実際の記録の不一致(本来0のはず、実装理解の検証) | 0 |
| **`appeasement=True`と`appeasement=False`で手の系列が異なった対戦数** | **0 / 30,420** |
| **Gradual と GradualAppeasement の実際の記録が完全一致した対戦数** | **30,420 / 30,420(100.00%)** |
| なだめ状態(`calm_remaining`)が内部的に発動した回数(全対戦合計) | 25,050 |
| なだめ状態が発動している間に出された行動の回数 | 13,200 |
| 罰(punishment)が対戦の最後(100ラウンド目)まで続いた対戦の割合 | 15,120 / 30,420(49.7%) |

### 原因:実装のバグ(事前登録・本番データの変更は提案しない)

`evopersonality_abm/strategies.py`の`make_gradual_strategy`は次の3分岐で行動を決める:

```python
if state["punish_remaining"] > 0:
    ...
    return DEFECT
if state["calm_remaining"] > 0:
    ...
    return COOPERATE          # ← なだめ中
return COOPERATE               # ← 通常時(なだめなしの場合はここが常に使われる)
```

**「なだめ中」の分岐も、「通常時」の分岐も、どちらも`COOPERATE`を返す**。つまり
`calm_remaining`という内部状態は確かに頻繁に(30,420対戦中25,050回)発動しているが、
発動してもしなくても出力される行動が変わらないため、外から見える振る舞いに
一切影響しない。さらに、罰の最中に新たな裏切りが来た場合は`calm_remaining`の値に
関係なく即座に罰が延長される(`if opp_history[-1] == DEFECT: ... state["calm_remaining"] = 0`が
罰・なだめの判定より先に無条件で実行される)ため、「なだめ中は多少の裏切りを大目に見る」
という本来の意図どおりの保護効果も実装されていない。

結論として、**GradualAppeasementはバグにより、現状ではGradual(なだめなし)と完全に同一の
振る舞いしかしない**。これは「なだめがほとんど発動しない」という頻度の問題ではなく
(内部的には対戦の82%相当の頻度で発動している)、発動しても観測可能な効果が無いという
実装上の不具合である。記述的な結果(6-7節)でGradualAppeasementの数値がGradualと小数第3位まで
一致していたのは、ブートストラップ抽出の乱数ストリームが異なるにもかかわらず
(ゲームプレイ自体が完全に同一であるため)数値が実質的に同一になった結果であり、
集計コードの不具合ではなくゲーム戦略の実装の不具合である。

修正案としては、罰の判定より先に「なだめ中は新たな裏切りを無視する(または罰のカウントに
加算しない)」処理を追加し、かつ`calm_remaining`中と通常時を区別できる行動
(例えば異なる内部状態としてログに残す、または将来的な拡張で行動セットを増やす)を
用意する必要があるが、**本番の確証的分析・記述的分析は事前登録どおりの実装で既に完走しており、
この報告の時点ではコードを修正しない**(修正すると、確証的分析の対象である主条件・感度分析の
評価ラン自体をやり直す必要が生じ、事前登録された分析計画の対象外になるため)。
修正を行うかどうかは別途判断を仰ぐ。

## 5. 既知の制約・注意点

  (70 seed)に対して効果量が小さい可能性がある。

- Table 12の閾値刻み(0.05〜0.70、0.05刻み、14点、長さ6まで)は、事前登録では明示されていなかった
  部分の操作的定義であり、`docs/CLARIFICATION_markov_cycle_thresholds.md`に本番データ分析前の決定
  として記録済み。
